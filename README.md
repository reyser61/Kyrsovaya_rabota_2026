# MailGuard — система анализа почтовых логов (IMAP/SMTP) для выявления фишинга и утечек

Курсовой проект. Программный комплекс на Python, который разбирает логи почтовых
серверов **Postfix (SMTP)** и **Dovecot (IMAP)**, а также исходные письма `.eml`,
применяет набор детекторов и формирует список инцидентов безопасности с оценкой
риска, веб-дашбордом и экспортом отчётов.

---

## 1. Назначение и возможности

Система анализирует данные на **двух уровнях**:

1. **Метаданные** — из логов Postfix/Dovecot (заголовки писем, события входа);
2. **Содержимое** — из исходных писем `.eml` (тело, ссылки, вложения).

Контентные правила (манипуляции, ПДн, секреты, выманивание данных) работают по
**теме И телу письма одновременно**. Логи и письма `.eml` объединяются в единую
запись по **Message-ID** (корреляция), что даёт детекторам максимум контекста.

| Категория | Что выявляет (метаданные) | Что выявляет (тема/тело и вложения) |
|-----------|---------------------------|-------------------------------------|
| **Фишинг** | спуфинг внутреннего домена, провал SPF/DKIM/DMARC, домены-двойники, punycode/IDN, расхождение Reply-To, массовые рассылки, несоответствие HELO | манипулятивные паттерны, выманивание учётных данных; ссылки на IP, сокращатели, подмена ссылки (текст ≠ href), домены-двойники и punycode в ссылках, опасные TLD; опасные вложения (.exe/.js/.hta…), двойные расширения, макро-документы, опасный файл внутри ZIP, запароленные архивы, HTML-вложения |
| **Утечки (DLP)** | крупные письма наружу, отправка на личную почту, вне рабочего времени, эксфильтрация | провалидированные ПДн (карта по Луну, СНИЛС/ИНН по контрольной сумме, паспорт, счёт), конфиденциальные слова, секреты/ключи/токены; чувствительные вложения (.sql/.xlsx/.pst…) наружу |
| **Компрометация аккаунтов** | брутфорс IMAP, захват ящика, «невозможное перемещение», вход без TLS | — |

Признаки одного письма **агрегируются** в один инцидент и оцениваются по модели
**«Ущерб × Достоверность»** (см. §5): у каждого правила есть уровень достоверности
(strong / medium / weak), одиночные слабые сигналы не поднимают тревогу, а
серьёзность ограничена достоверностью — это резко снижает ложные срабатывания.
Из подтверждённых инцидентов формируется база **индикаторов компрометации (IoC)**.

```powershell
py -m pip install -r requirements.txt
```

> Flask и PyYAML, остальное — стандартная библиотека.

## 4. Быстрый старт

**В один клик (Windows):** дважды кликните **`start_mailguard.bat`** — он установит
зависимости, прогонит тесты, сгенерирует данные, проведёт анализ, запустит
веб-дашборд и откроет браузер на `http://127.0.0.1:5000`.

Либо вручную:

```powershell
py tools/generate_sample_logs.py
py tools/generate_sample_emails.py
py run.py analyze --postfix data/sample_logs/postfix.log --dovecot data/sample_logs/dovecot.log --emails data/sample_emails --save
py run.py web        # http://127.0.0.1:5000
```

Любой аргумент необязателен — можно анализировать только логи, только письма или
всё вместе. Экспорт отчёта: `--report report.html --format html` (или `csv`/`json`).

## 5. Оценка риска: модель «Ущерб × Достоверность»

Реализована в [`mailguard/scoring.py`](mailguard/scoring.py):

1. **Достоверность правила** — `strong` (убедителен сам по себе), `medium`
   (значим, но не доказателен), `weak` (норма в быту, значим лишь в сочетании).
2. **Агрегация** — все признаки письма по категории собираются в один инцидент.
3. **Порог тревоги** — одиночный слабый сигнал инцидента не создаёт.
4. **Балл с затуханием** — веса суммируются с коэффициентами `1.0, 0.6, 0.4,
   0.25…`, чтобы стопка слабых сигналов не раздувала риск.
5. **Достоверность инцидента**: высокая — сильный + ещё один; средняя — один
   сильный или ≥2 средних; низкая — иначе.
6. **Серьёзность ограничена достоверностью**: `critical` — только при высокой.
7. **Allow-list** доверенных партнёров (`trusted_domains`) не алертит на слабых
   сигналах (но `exe`, валидные ПДн и т.п. срабатывают всегда).

| Балл (с затуханием) | Уровень |
|---------------------|---------|
| 0–29 | низкая |
| 30–49 | средняя |
| 50–74 | высокая |
| 75+ | критическая |

На демо-данных модель снизила число инцидентов с 41 до 16 без потери угроз.

# 8. ПРАВИЛА: как написаны, на чём основаны, какой синтаксис

Правило — это единица знания о признаке угрозы. В системе **два вида правил**:
**встроенные** (логика в коде + метаданные в реестре) и **декларативные**
(правила-данные, создаются пользователем). Все правила собраны в **реестр**
[`mailguard/rules.py`](mailguard/rules.py) (класс `RuleRegistry`), который — единый
источник истины для движка и веб-панели.

### 8.1. Анатомия встроенного правила

Каждое встроенное правило описывается объектом `Rule` в функции `_builtin_rules()`
(файл `rules.py`). Пример:

```python
R("phishing.dmarc_fail", "Провал DMARC",
  "Письмо не прошло проверку политики DMARC домена отправителя.",
  "phishing", 35, "medium", section="phishing", key="dmarc_fail",
  mitre=["T1566", "T1656"], rfc=["RFC 7489"]),
```

Поля:

| Поле | Назначение |
|------|------------|
| `id` | уникальный идентификатор (`phishing.dmarc_fail`) — по нему правило связано с кодом и отображается в инциденте |
| `name` | человекочитаемое название |
| `description` | что именно проверяет |
| `category` | `phishing` / `dlp` / `account` |
| `default_weight` | вес (ущерб) по умолчанию |
| `confidence` | достоверность: `strong` / `medium` / `weak` |
| `section`, `key` | откуда брать вес из `config.yaml` (секция → `weights` → ключ) |
| `mitre`, `rfc` | **обоснование**: техники MITRE ATT&CK и стандарты |

Само **срабатывание** правила реализовано в соответствующем детекторе
(`mailguard/detectors/`). Детектор — «поставщик признаков»: он не выносит вердикт,
а возвращает объекты `Finding(rule_id, category, reason, evidence)`. Например,
проверка DMARC в `detectors/phishing.py`:

```python
if rec.dmarc == "fail":
    add("phishing.dmarc_fail", "отправитель не прошёл проверку подлинности DMARC")
```

Дальше движок передаёт все `Finding` в `scoring.assess()`, который агрегирует их в
инцидент (см. §5).

### 8.2. На чём основаны правила

Признаки опираются на отраслевые стандарты и общепринятые модели угроз:

| Основание | Что покрывает |
|-----------|---------------|
| **RFC 7208 / 6376 / 7489** | SPF / DKIM / DMARC — аутентификация отправителя |
| **RFC 5321** | SMTP — корректность HELO/EHLO |
| **RFC 3207** | STARTTLS — шифрование сессии (вход без TLS) |
| **RFC 3492** | Punycode / IDN — домены-омоглифы |
| **MITRE ATT&CK** | T1566 фишинг (.001 вложение, .002 ссылка), T1036.007 двойное расширение, T1110 брутфорс, T1078 валидные УЗ, T1048/T1567 эксфильтрация, T1552 секреты, T1656 импersonation |
| **ФЗ-152, ISO/IEC 7812** | персональные данные; алгоритм Луна для номеров карт |

Числовые **веса** правил — экспертная калибровка, вынесенная в `config.yaml`.

### 8.3. Типы правил по методу обнаружения

| Тип / метод | На что нацелен | Правила (id) |
|-------------|----------------|--------------|
| Аутентификация (метаданные) | подделка отправителя | `phishing.dmarc_fail`, `spf_fail`, `dkim_fail`, `spoofed_internal`, `helo_mismatch`, `replyto_mismatch` |
| Анализ домена | домены-двойники, IDN | `phishing.lookalike_sender`, `punycode_sender` |
| Поиск по словам | манипуляции, выманивание, конфиденц. слова | `phishing.manipulative_content`, `credential_request`, `dlp.confidential_keyword` |
| Шаблоны (regex) + валидация | ПДн, секреты, ключи | `dlp.pii`, `dlp.secret_exposure` |
| Анализ ссылок (URL) | фишинговые ссылки | `phishing.url_ip_literal`, `url_text_mismatch`, `url_shortener`, `url_suspicious_tld`, `url_lookalike`, `url_punycode` |
| Анализ вложений | ВПО и утечка файлов | `phishing.attachment_dangerous`, `double_ext`, `real_macro`, `macro`, `archive`, `archive_inner`, `encrypted`, `html`; `dlp.attachment_highrisk`, `attachment_office`, `attachment_large` |
| Поведенческие / количественные | массовость, объём, время, эксфильтрация | `phishing.mass_recipients`, `dlp.free_mail_recipient`, `large_external`, `off_hours`, `exfiltration` |
| Компрометация (IMAP) | брутфорс, захват, гео-аномалии | `account.bruteforce`, `takeover`, `impossible_travel`, `plaintext_login` |
| Сверка с блок-листом IoC | известные вредоносные индикаторы | `ioc.match_ip`, `match_email`, `match_domain`, `match_file_hash`, `match_subject` |

- **Поиск по словам** — словари в `config.yaml` (`contains_any`).
- **Шаблоны + валидация** — regex + контрольные суммы (`find_pii`): номер карты по
  алгоритму Луна, СНИЛС/ИНН по контрольным цифрам — это отсекает случайные числа.
- **Анализ вложений** — расширения + реальная инспекция: распаковка ZIP, поиск
  файла `vbaProject.bin` (признак макроса), SHA-256.

### 8.4. Где задаются веса и достоверность

**Вес** правила берётся из `config.yaml` по паре `section`/`key`. Например, для
`phishing.dmarc_fail` (section=`phishing`, key=`dmarc_fail`):

```yaml
phishing:
  weights:
    dmarc_fail: 35
    auth_fail: 30
    spoofed_internal: 40
```

**Достоверность** (`strong`/`medium`/`weak`) задаётся в самом объекте `Rule`
(в коде) и отражает, насколько признак убедителен сам по себе.

### 8.5. Декларативные правила — синтаксис (data/rules.yaml)

Пользовательские правила — это **данные, а не код** (безопасно, как Sigma/YARA).
Хранятся в [`data/rules.yaml`](data/rules.yaml) и исполняются `ContentDetector` по
теме/телу письма. Синтаксис:

```yaml
rules:
- id: custom.brand_lure            # уникальный id (префикс custom.)
  name: Приманка под известный бренд
  description: Упоминание бренда-приманки в теме/теле.
  category: phishing               # phishing | dlp
  weight: 20                       # балл (ущерб)
  confidence: medium               # strong | medium | weak
  enabled: true                    # включено ли
  rtype: keyword                   # keyword | regex
  field_scope: both                # subject | body | both (область поиска)
  patterns:                        # список шаблонов
  - сбербанк
  - госуслуги
  - налоговая
  mitre:                           # (опционально) техники MITRE
  - T1566
```

Поля декларативного правила:

| Поле | Значения | Смысл |
|------|----------|-------|
| `id` | строка | уникальный идентификатор (рекомендуется префикс `custom.`) |
| `category` | `phishing` / `dlp` | категория инцидента |
| `weight` | число | вес (ущерб) |
| `confidence` | `strong` / `medium` / `weak` | достоверность |
| `rtype` | `keyword` / `regex` | метод: вхождение слов или регулярное выражение |
| `field_scope` | `subject` / `body` / `both` | где искать |
| `patterns` | список строк | слова или regex-шаблоны (любое совпадение → срабатывание) |
| `enabled` | `true` / `false` | активно ли правило |

> `phishing`-правила применяются к входящим письмам, `dlp` — к исходящим внешним
> адресатам (как и встроенные правила соответствующих категорий).

### 8.6. Как добавить своё правило

**Способ 1 — через веб (рекомендуется):** вкладка **«Правила» → «Создать своё
правило»** (название, категория, тип, область, шаблоны, вес). Правило сохранится в
`data/rules.yaml` и применится при следующем анализе.

**Способ 2 — вручную в `data/rules.yaml`** по синтаксису из §8.5.

**Способ 3 — встроенное правило (в коде):** добавить объект `Rule` в
`_builtin_rules()` (`rules.py`), задать вес в `config.yaml` и реализовать
срабатывание в нужном детекторе (вернуть `Finding(rule_id, ...)`).

### 8.7. Включение и выключение правил

Любое правило можно выключить на вкладке «Правила»; состояние встроенных правил
хранится в `data/rules_state.json` (создаётся автоматически), выключенное правило
даёт 0 баллов и не участвует в анализе.

## 9. Индикаторы компрометации (IoC) и блок-лист

Из **подтверждённых** инцидентов (серьёзность ≥ `ioc.min_severity`, по умолчанию
`high`) формируется база IoC ([`mailguard/ioc.py`](mailguard/ioc.py)): IP, e-mail и
домены отправителей, домены из ссылок, SHA-256 вложений, темы. Свои/доверенные
домены и приватные IP не включаются.

Известные вредоносные индикаторы ведутся в блок-листе
([`data/ioc_blocklist.csv`](data/ioc_blocklist.csv), формат `type,value,source,added`).
При анализе индикаторы письма сверяются с ним — совпадение даёт **сильный** сигнал
(правила `ioc.match_*`). Пополнение:

```powershell
py run.py blocklist show
py run.py blocklist import --file feed.csv
py run.py blocklist promote        # перенести собранные high/critical IoC в блок-лист
```
